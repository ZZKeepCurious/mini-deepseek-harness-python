# 文档写作规范（报告与教程手册通用）

> 本项目的所有文档（`docs/report/`、`docs/chapters/`、README、任何新增文档）一律遵守本规范。
> 目标读者：第一次接触 dsh 的开发者。目标效果：像一个人认真整理过的长文笔记，而不是 AI 生成的汇报。

## 1. 视角与口吻

1. **教程式、分享式视角**：以"通常的做法 → dsh 的做法 → 差异 → 源码证据"的对比推进，而不是以"全局上帝视角"直接下结论。
2. **禁止个人散文**：不写"我读得最慢""我以前以为""我踩过坑""我的学习过程"这类过程叙述。读者要的是知识本身，不是作者的历程。
3. **允许个人观点，禁止个人过程**：可以写"这个设计优于常规做法，因为……"，不可以写"我花了三天才看懂"。观点是内容，过程是噪音。
4. **直接与读者对话**：使用"你"和第二人称建议（"建议你……""你会看到……"），但不要频繁使用。

## 2. 结构编排

1. **打破对称模板**：不要每章、每节都用同一套结构（如"步骤 1/2/3 → 回到源码 → 小结"）。该展开的展开，该略过的略过；对照内容能融进行文的就融进行文，不必单独设节。
2. **先直觉后定义**：每个概念先给"为什么需要它"（动机/反例），再给定义，最后给代码或证据。
3. **标配反事实讨论**：关键设计处回答"为什么不反过来做？"（例如：为什么存事件日志而不直接存消息数组？为什么 replace 不删旧事件？），这是教程最有效的部分。
4. **结论自然收尾**：不用"本章小结"表格。结尾可以预告下一步或抛出思考题，一句话即可。
5. **编号列表逐行排布**：1、2、3、4 的罗列必须逐行排列，禁止挤在同一行；每条保持简短，必要时拆成多条。

## 3. 语言与修辞

1. **去 AI 排比**：禁止对仗标题、排比句、过度破折号（"——"一行内最多出现一次，避免连续使用）。
2. **加粗减半**：只加粗真正的术语定义或关键结论（每节不超过 2~3 处），禁止把每个小标题都加粗成"术语卡"。
3. **修辞平实**：标题和正文用平实说法。"核心中的核心""牵一发动全身""物理保证"这类书面化修辞一律不用；换成"这是整个框架的地基""改动会波及全部下游"这类直接表述。
4. **术语口语化**：以下术语按约定替换（可保留一次原文对照，例如括号注明英文）：
   - 契约 → 约定（或"接口约定"）
   - 不变量 → 硬性规定（或"始终成立的性质"）
   - 接缝 → 扩展口（或"可替换点"）
   - 心智模型 → 直观理解
   - 单一事实来源 → 唯一数据源
   - 上帝视角/全局视野 → 直接删掉
5. **允许口语化表达**：可以用"说白了""换句话说"这类连接词，但每段不超过一次；整体保持信息密度。

## 4. 内容要求

1. **源码证据**：涉及 dsh 真实行为的论断，必须能定位到 `packages/` 或 `docs/` 下的具体路径；无法定位的视为"学习归纳"，必须标注。
2. **诚实标注简化**：简化实现与上游的差异必须明说，格式："上游是 X（源码位置）；本章实现为 Y（原因）"。
3. **代码块与真实代码一致**：教程中的代码示例必须与 `miniharness/` 下的真实代码逐字一致（可省略类型注解，但逻辑、字段名、错误信息必须一致）。
4. **不默认读者会**：涉及的专业概念（事件溯源、SSE、声明合并等）第一次出现时必须给一句直觉解释；禁止"显然""众所周知"。

## 5. 排版细节

1. 中文与英文/代码之间保留一个空格；中文标点使用全角。
2. Mermaid 图内禁止裸 `<br/>`，一律写 `&lt;br/&gt;`（否则 v10 UMD 加载会报错）。
3. 长句拆短句：单句超过 60 字必须拆分。
4. HTML 报告同样遵守以上所有条款（列表用 `<ol>`/`<ul>` 逐项、正文用 `<p>` 分段、禁止把多项枚举挤进一个 `<li>`）。

## 6. 写作前自检清单

- [ ] 全文没有"我"的第一人称过程叙述（观点性"我认为"除外）
- [ ] 没有对仗标题、排比句、术语卡式加粗轰炸
- [ ] 每个关键设计都有"常规做法 vs dsh 做法"的对比或反事实讨论
- [ ] 每个涉及上游的论断都有源码路径可查
- [ ] 代码示例与真实代码一致
- [ ] 结构允许不齐整（该长的长、该短的短），没有模板感
